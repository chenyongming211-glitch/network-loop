# Delivery C.1 GitHub Build Supply-Chain Hardening Design

**Date:** 2026-08-11
**Status:** Approved for specification review
**Parent:** `docs/superpowers/specs/2026-08-10-isolated-passive-observation-design.md`

## 1. Goal

Delivery C.1 makes every repository-controlled build input explicit before rate-window development begins. It commits the exact Cargo dependency graph, pins GitHub Actions and Rust/eBPF build tools, requires locked dependency resolution, and adds permanent CI checks that reject regression to floating inputs.

This delivery preserves the existing operating model:

- all Cargo, Rust, eBPF, formatting, linting, and automated tests run only in GitHub Actions;
- development commits go directly to `main`;
- the GitHub workflow keeps `contents: read` permission;
- no local command compiles code or resolves Rust dependencies;
- authorized host acceptance uses only the exact successful GitHub artifact;
- no physical, business, shared, bridge, bond, OVS, tap, route, address, sysctl, offload setting, service, or foreign BPF object is changed.

## 2. Reproducibility Boundary

Delivery C.1 guarantees deterministic repository-controlled inputs:

- the complete Cargo package graph and checksums;
- GitHub Action implementation commits;
- stable and nightly Rust toolchains;
- `bpf-linker` package version;
- Cargo locked-resolution behavior in every build path;
- the exact source commit and bundle checksums already recorded by the release artifact.

It does not claim byte-for-byte reproducible binaries. GitHub-hosted runner images, preinstalled operating-system tools, download mirrors, archive metadata, timestamps, and underlying infrastructure remain outside the repository-controlled boundary.

The accepted artifact and its `SHA256SUMS` remain the deployment authority. A later delivery may use a digest-pinned build container and reproducible-build comparison if byte identity becomes a requirement.

## 3. Current Risks Being Closed

The Delivery C audit confirmed these mutable inputs:

- no tracked root `Cargo.lock`;
- all twelve `uses:` entries refer to release tags or moving branches;
- `rust-toolchain.toml` selects `stable`;
- CI selects `stable` and undated `nightly`;
- `cargo install bpf-linker --locked` does not select a package version;
- `xtask` invokes `cargo +nightly build` internally;
- build, check, test, Clippy, bundle, and eBPF resolution paths do not uniformly require the root lock file.

No Delivery C runtime safety failure was found. This delivery is build-provenance hardening and does not change packet classification, observation, attachment, ownership, cleanup, protocol, or CLI semantics.

## 4. Fixed Input Contract

### 4.1 GitHub Actions

Every remote Action reference uses a full 40-character commit SHA. A trailing comment records the human-readable release or channel that was verified in the final Delivery C run.

| Action | Human reference | Fixed commit |
|---|---|---|
| `actions/checkout` | `v5` | `fbc6f3992d24b796d5a048ff273f7fcc4a7b6c09` |
| `actions/upload-artifact` | `v7` | `043fb46d1a93c77aae656e7c1c64a875d1fc6a0a` |
| `actions/download-artifact` | `v8` | `3e5f45b2cfb9172054b4087a40e8e0b5a5461e7c` |
| `dtolnay/rust-toolchain` stable invocation | `stable` at the Delivery C gate | `4360b52568e2003a75bf9bc1d59f33a8e3fc893c` |
| `dtolnay/rust-toolchain` nightly invocation | `nightly` at the Delivery C gate | `7c8d7d138f5c09cef361f8214cf96882cd029cdb` |

The explicit `toolchain` input, not the Action branch name, selects Rust. An Action SHA update and a Rust version update are separate reviewable changes even when performed in one atomic maintenance commit.

### 4.2 Rust and eBPF tools

The fixed versions are:

| Input | Fixed value |
|---|---|
| stable Rust | `1.97.1` |
| eBPF nightly Rust | `nightly-2026-08-10` |
| `bpf-linker` | `0.10.4` |

`rust-toolchain.toml` selects `1.97.1` with the existing minimal profile, Clippy, and rustfmt components. Each stable CI invocation supplies `toolchain: 1.97.1`. The eBPF job supplies `toolchain: nightly-2026-08-10` with `rust-src`.

The linker install command is exactly:

```text
cargo install bpf-linker --version 0.10.4 --locked
```

This locks the linker package's own published dependency graph. It is independent from the workspace root `Cargo.lock`.

### 4.3 Workspace dependency graph

A root `Cargo.lock` generated by GitHub is committed to `main`. It covers every workspace member, including `l2-loop-ebpf` and `xtask`.

Commands that build, check, test, lint through Cargo, run `xtask`, or query the resolved graph must refuse lock-file changes. The permanent commands include:

```text
cargo metadata --locked --no-deps
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
cargo check --locked
cargo build --locked --release --target x86_64-unknown-linux-musl ...
```

The `.cargo/config.toml` alias becomes:

```toml
[alias]
xtask = "run --locked --package xtask --"
```

`cargo fmt --all -- --check` is exempt because rustfmt does not resolve the dependency graph.

### 4.4 Exact inner eBPF build

`xtask` owns the eBPF subprocess contract. It invokes:

```text
cargo +nightly-2026-08-10 build --locked -Z build-std=core --release \
  --target bpfel-unknown-none --package l2-loop-ebpf
```

The argument construction moves into a small library function with unit tests. The binary uses only that function, so the tested exact toolchain and `--locked` arguments are the production invocation.

## 5. GitHub-Only Lock Bootstrap

The initial lock file cannot be generated locally. The bootstrap is a bounded two-commit RED/GREEN process around one temporary workflow.

### 5.1 RED commit

The RED commit adds:

- a permanent PowerShell supply-chain contract test;
- Linux and Windows CI invocation of that test;
- a temporary, manually dispatched lock-bootstrap workflow.

The normal CI run must fail for the intended reasons: the lock file is absent and the existing permanent CI workflow still contains mutable inputs. The temporary workflow itself uses only the fixed Action SHAs, exact stable Rust, and `contents: read`.

### 5.2 Bootstrap artifact

The temporary workflow:

1. checks out the exact RED commit;
2. installs stable Rust `1.97.1` through the fixed Action SHA;
3. runs `cargo +1.97.1 generate-lockfile`, explicitly overriding the still-moving `rust-toolchain.toml` present in the RED commit;
4. runs `cargo +1.97.1 metadata --locked --no-deps` to prove the generated lock is self-consistent with the same Cargo version;
5. uploads exactly `Cargo.lock` as `l2-loop-cargo-lock-<full-commit-sha>` with one-day retention.

It never compiles, commits, pushes, opens a pull request, or obtains write permission.

The local authoring host downloads the one exact artifact through `gh run download`, verifies that the artifact contains exactly one regular file named `Cargo.lock`, and moves that file into the repository using a reviewed patch operation. It does not run Cargo.

### 5.3 GREEN commit

The GREEN commit:

- removes the temporary bootstrap workflow;
- commits the generated root lock file;
- pins permanent Action references and toolchains;
- pins `bpf-linker`;
- adds locked Cargo resolution;
- implements and tests the exact xtask eBPF command;
- updates operator documentation.

The final repository contains no workflow capable of generating or committing dependency updates automatically.

## 6. Permanent Supply-Chain Gate

`scripts/tests/verify-build-supply-chain.Tests.ps1` is a self-contained static test that runs under both Linux PowerShell 7 and Windows PowerShell. It reads only tracked repository files and performs no network request.

It requires:

- a tracked, non-empty root `Cargo.lock` with the Cargo lock format header;
- every active `.github/workflows/*.yml` remote `uses:` reference to end in a full 40-character lowercase hexadecimal SHA followed by an optional version comment;
- `permissions: contents: read` and absence of `contents: write`;
- `rust-toolchain.toml` to contain `channel = "1.97.1"`;
- permanent CI stable inputs to equal `1.97.1`;
- the eBPF nightly input to equal `nightly-2026-08-10`;
- `bpf-linker` installation to include both `--version 0.10.4` and `--locked`;
- every workspace-resolving permanent CI command to use locked resolution;
- the xtask alias to contain `run --locked --package xtask --`;
- no active workflow reference to `@stable`, `@nightly`, a version tag, a branch name, or a shortened SHA.

The test does not parse arbitrary YAML semantics. It checks the deliberately small, fixed workflow surface using anchored line patterns and exact required strings. Rust unit tests separately verify the xtask argument vector, avoiding a fragile source-text assertion for production Rust behavior.

## 7. Test-First Delivery

The implementation uses two independent RED/GREEN proofs:

1. **Repository policy RED/GREEN:** the PowerShell contract test fails on the mutable baseline in the RED commit and passes only after the lock, pins, and locked commands are present.
2. **xtask behavior RED/GREEN:** a Rust test first expects the exact dated nightly and locked argument vector; GitHub Userspace fails until the production argument builder and binary integration are implemented.

No local test result is reported as compilation evidence. Local work is limited to `git`, `rg`, file inspection, patching, artifact download, checksum inspection, and other non-Cargo static checks.

## 8. Failure Semantics

| Failure | Required result |
|---|---|
| Bootstrap workflow is absent or dispatch fails | Stop; do not generate locally |
| Bootstrap run is not for the exact RED SHA | Reject the artifact |
| Lock artifact is missing, expired, duplicated, or has extra files | Reject it without changing the repository |
| `cargo metadata --locked` rejects the generated lock | Bootstrap run fails and uploads no accepted lock |
| Permanent workflow contains a mutable Action reference | Linux and Windows supply-chain tests fail |
| Manifest and lock file disagree | Locked Cargo command fails before an accepted bundle exists |
| Stable, nightly, or linker version drifts | Static gate or exact xtask test fails |
| Exact final CI does not publish one matching bundle | No authorized-host acceptance is run |
| Host acceptance fails | Delivery C.1 remains incomplete; cleanup and residue audit still run |

No build-provenance failure changes the runtime cleanup authority or permits a fallback build on the local host.

## 9. Permissions and Update Policy

All workflows retain top-level:

```yaml
permissions:
  contents: read
```

No workflow receives repository write, package write, deployment, identity-token, issue, or pull-request permission. No dependency updater, automatic pull request, scheduled update, or bot commit is introduced.

Future dependency, Rust, linker, or Action changes are manual and atomic. The maintainer explicitly selects new versions, regenerates the lock through a temporary read-only GitHub workflow, reviews the diff, and requires the complete CI and exact-artifact gate. This repository continues to push reviewed commits directly to `main`.

## 10. Final Verification

The final GREEN commit must provide:

1. successful Linux and Windows supply-chain contract tests;
2. successful formatting, Clippy, tests, and workspace check under stable Rust `1.97.1`;
3. successful eBPF build under `nightly-2026-08-10` and `bpf-linker 0.10.4`;
4. successful MUSL bundle generation from locked dependencies;
5. exactly one six-file `l2-loop-linux-x86_64-<full-commit-sha>` artifact;
6. valid bundle `SHA256SUMS`;
7. authorized isolated `Success` and `PassiveObservation` scenarios against that exact artifact;
8. an independent residue audit proving no generated namespace, veth, runtime path, pin path, or owned attachment remains;
9. a clean worktree with `HEAD` equal to `origin/main`.

The two host scenarios are sufficient because C.1 changes only build inputs and the eBPF build command. `Success` proves the complete load/attach/count/detach transaction, and `PassiveObservation` proves the Delivery C parser, classification, Map reader, daemon/CLI, forwarding, and cleanup path from the rebuilt artifact.

## 11. Explicit Non-Goals

Delivery C.1 does not add:

- byte-for-byte reproducible build claims;
- a pinned runner image or build container;
- vendored Rust crates;
- dependency vulnerability scanning or an advisory database;
- artifact signing, provenance attestations, or a transparency log;
- automatic dependency updates or pull requests;
- a release registry or long-term artifact archive;
- any packet-path, ABI, Map, journal, control protocol, CLI, attachment, observation, or cleanup behavior;
- PPS/BPS sampling, sliding windows, dynamic baselines, fingerprints, loop decisions, probes, drops, or policing.

Those controls may be designed separately. The next functional delivery after C.1 remains the bounded daemon sampler and explicit PPS/BPS windows.

## 12. Acceptance Criteria

Delivery C.1 is complete only when:

1. the root `Cargo.lock` was generated by one exact GitHub bootstrap run and is tracked;
2. every active remote Action reference is a reviewed full SHA;
3. stable Rust, dated nightly Rust, and `bpf-linker` equal the fixed contract;
4. every dependency-resolving build path refuses lock changes;
5. the static gate fails on the pre-hardening baseline and passes on the final state;
6. the xtask test fails before and passes after exact inner eBPF command implementation;
7. the temporary bootstrap workflow is absent from the final tree;
8. all five final CI jobs pass for one exact `main` commit;
9. the exact bundle passes `Success` and `PassiveObservation` on the authorized node;
10. host residue, prohibited-identifier, credential-material, unsafe-command, and packet-drop audits remain clean.
