# Local Alert and Evidence Output Design

**Date:** 2026-08-06  
**Status:** Approved design; implementation plan not yet written  
**Scope:** Local alert publication, bounded evidence persistence, and local CLI queries  
**Supersedes:** The alert and evidence-output details in `docs/l2-loop-agent-design.md` and placeholder evidence result shapes in the Rust foundation specification where they conflict with this document

## 1. Decision

The L2 Loop Detection Agent uses three local output layers:

1. a versioned, bounded evidence store as the authoritative incident record;
2. native structured journald events as concise, best-effort notifications;
3. `l2-loopctl status` and `l2-loopctl evidence` as the supported operator query path.

The first delivery does not export Prometheus metrics, configure Alertmanager, send webhooks, email, SMS, or chat notifications, or introduce a database or message queue. Raw packet captures are not returned through the control socket.

The required data flow is:

```text
loop-state transition
  -> build AlertEventV1 and assign EventId
  -> build EvidenceBundleV1
  -> persist the evidence bundle atomically
       -> stored: publish a journald summary with evidence_status=stored
       -> failed: publish a journald summary with evidence_status=unavailable
                  and mark output health degraded
  -> serve sanitized status and evidence views through the local control socket
```

Evidence persistence is the source of truth. Journald is not a database and may rate-limit messages. A journald entry never proves that the evidence bundle was committed; the `evidence_status` field states the result explicitly.

## 2. Goals

- Preserve every material loop-state transition with a stable event identity.
- Keep packet-path and detection work independent from filesystem and journald failures.
- Make power loss, disk exhaustion, corrupt files, and daemon restarts observable.
- Bound disk, memory, protocol-response, and log volume.
- Let an authorized local operator find the active event and inspect sanitized evidence quickly.
- Keep raw packet and topology material root-only.
- Maintain stable, versioned JSON models for files and control responses.

## 3. Non-goals

- Monitoring-platform metrics or dashboards.
- Remote alert delivery or retry queues.
- A SQL, embedded, or distributed database.
- A general-purpose event bus.
- Automatic packet-capture export.
- Returning raw PCAP bytes through the one-megabyte control protocol.
- Treating a log line as durable incident evidence.
- Changing loop-classification thresholds or the detection state machine itself.

## 4. Alternatives Considered

### 4.1 Journald only

Rejected. It is operationally simple but cannot be the evidence authority because messages can be rate-limited, retention is host-wide, and a log entry cannot atomically include the complete bounded evidence bundle.

### 4.2 Database or message queue

Rejected for the first release. A database would add schema migration, corruption recovery, packaging, and operational dependencies without improving the single-node, bounded-event use case. A message queue would add delivery semantics for remote consumers that are explicitly out of scope.

### 4.3 Bounded files plus journald summaries and CLI queries

Selected. It reuses the existing `EvidenceStore`, local protocol, and CLI boundaries while keeping the durable format inspectable and recoverable with ordinary Linux tools.

## 5. Domain Models

All serialized names use `snake_case`. All models carry `schema_version: 1`. Unknown enum values are rejected; unknown additive object fields are ignored so readers can tolerate compatible extensions.

### 5.1 `EventId`

`EventId` is a dedicated value type containing 16 random bytes rendered as 32 lowercase hexadecimal characters. It is generated by the daemon and never derived from a hostname, interface name, MAC address, wall-clock timestamp, or user input.

Parsing requires exactly 32 ASCII hexadecimal characters in canonical lowercase form. `/`, `\`, `.`, whitespace, separators, Unicode, and non-canonical encodings are rejected before any filesystem lookup.

### 5.2 `AlertEventV1`

```rust
pub struct AlertEventV1 {
    pub schema_version: u16,
    pub event_id: EventId,
    pub transition_sequence: u64,
    pub logical_interface: InterfaceName,
    pub attachment_interface: InterfaceName,
    pub ifindex: u32,
    pub interface_generation: u64,
    pub previous_state: LoopState,
    pub current_state: LoopState,
    pub code: AlertCode,
    pub severity: AlertSeverity,
    pub occurred_at: String,
    pub monotonic_ns: u64,
    pub evidence_id: EventId,
    pub evidence_status: EvidenceStatus,
}
```

`occurred_at` is UTC RFC 3339 with nanosecond precision when available. `monotonic_ns` is used only for ordering within one daemon boot. Ordering across restarts uses `occurred_at`, then `event_id`; the design does not expose a machine or boot identifier.

`transition_sequence` starts at one for each event and increases for every persisted state transition. A continuing sample that does not change state or materially change evidence does not create a new alert event.

### 5.3 Severity

```text
information  -> lifecycle information and recovery
notice       -> storm confirmed or loop suspected
warning      -> loop high-confidence or output degraded
error        -> loop confirmed
```

Evidence persistence failure never downgrades the detection result. It changes `evidence_status` to `unavailable`, raises output health to degraded, and emits at least warning severity. The alert must not imply that complete evidence exists.

### 5.4 Evidence models

`EvidenceSummaryV1` is safe for the read-only operator group and contains:

- event ID and schema version;
- logical interface, attachment interface, ifindex, and generation;
- current and previous state;
- alert code and severity;
- opened, last-transition, and closed timestamps;
- ingress/egress PPS and BPS aggregates;
- VLAN visibility state and optional VLAN ID;
- evidence completeness and attachment availability;
- bundle byte size and integrity state.

It excludes raw MAC addresses, IP addresses, fingerprints, packet bytes, customer labels, foreign paths, and raw topology identifiers.

`EvidenceBundleV1` is root-only and contains the complete bounded record approved by the product design: the transition timeline, NIC and kernel resource snapshots, ingress/egress aggregates, protocol and BUM classification, fingerprints, local ownership and topology evidence, probe evidence, and attachment metadata.

`EvidenceManifestV1` contains:

- schema version and event ID;
- creation and last-update timestamps;
- state and completeness;
- exact file names, byte lengths, and SHA-256 values;
- total bundle size;
- whether an optional PCAP is present;
- the writer package version and evidence format version.

## 6. Evidence Store Layout

```text
/var/lib/l2-loop/evidence/
  v1/
    <event-id>/
      0000000000000001/
        manifest.json
        evidence.json
        capture.pcap        # optional, disabled by default
      0000000000000002/
        manifest.json
        evidence.json
```

The root and version directories are owned by `root:root` with mode `0700`. Bundle directories use `0700`; files use `0600`. Operators access sanitized views through the daemon. Direct filesystem access is not granted to the `l2-loop` group.

Each 16-digit decimal directory is an immutable state-transition revision. The highest valid revision is the current view; older revisions preserve the event timeline across crashes and upgrades.

The daemon opens the evidence root once, validates ownership and mode, and resolves children relative to that directory descriptor. It does not follow symbolic links. A parsed `EventId`, never a raw string, selects an event. Existing event and revision targets are never overwritten.

## 7. Atomic Commit and Recovery

One state transition commits as follows:

```text
create a same-directory private temporary event or revision
  -> write evidence.json and optional capture.pcap
  -> fsync every file
  -> write manifest.json last
  -> fsync manifest.json
  -> fsync the temporary directory
  -> rename it to the canonical event ID or transition sequence with no-replace semantics
  -> fsync the containing event or v1 directory
  -> publish the journald summary
```

The temporary and final directories are on the same filesystem. The first transition atomically publishes an event directory containing revision one. Later transitions atomically add a new immutable revision below the existing event directory. The implementation uses no-replace rename semantics supported by the target Linux kernel. An unexpected existing event ID or sequence is an error; it never replaces evidence.

On startup the store:

1. validates its root ownership and permissions;
2. scans only canonical event-ID directories and daemon-owned temporary names;
3. validates every revision manifest, length, and SHA-256 before indexing it;
4. selects the highest valid revision and excludes incomplete or corrupt revisions from normal results;
5. reports corrupt and incomplete counts through store health;
6. removes only temporary paths whose daemon-owned naming and age rules match;
7. never deletes an unknown file, directory, link, or non-canonical name.

The first implementation uses an in-memory index reconstructed from manifests. It does not persist a second index or add a database.

## 8. Boundedness and Retention

The initial defaults are:

```text
max_store_bytes       = 1 GiB
max_events            = 1,000
max_event_bytes       = 16 MiB
max_revision_structured_bytes = 1 MiB
max_age               = 30 days
min_free_bytes        = 512 MiB
min_free_percent      = 5
pcap_enabled          = false
pcap_max_bytes        = 8 MiB
pcap_max_duration     = 3 seconds
pcap_snaplen          = 128 bytes
```

The effective free-space reserve is the larger of `min_free_bytes` and `min_free_percent` of the evidence filesystem. Configuration may reduce the limits but may not remove all byte, count, age, and free-space bounds.

Before committing a bundle, retention runs in this order:

1. omit or stop the optional PCAP when it would exceed a per-event or free-space limit;
2. remove the oldest closed events until byte, count, age, and free-space limits are satisfied;
3. preserve active events and their structured evidence;
4. if structured evidence still cannot be committed, mark the store degraded and publish `evidence_status=unavailable`.

The daemon does not create evidence per packet or per sampling interval. It creates an event at incident open and adds one immutable revision per material state transition. Each revision contains the full bounded transition timeline so it can be interpreted independently. Retention removes whole closed-event directories, never individual valid revisions from an active event.

## 9. Journald Contract

The production daemon uses Rust `tracing` with the pure-Rust `tracing-journald` layer. It sends native journald fields rather than placing a nested JSON object in `MESSAGE`. Operators obtain JSON with `journalctl -o json` or `journalctl -o json-pretty`.

Every alert event includes:

```text
SYSLOG_IDENTIFIER=l2-loopd
MESSAGE_ID=6c326c6f6f706576656e743030303031
L2_SCHEMA_VERSION=1
L2_EVENT_ID=<event-id>
L2_TRANSITION_SEQUENCE=<n>
L2_CODE=<stable alert code>
L2_SEVERITY=<severity>
L2_PREVIOUS_STATE=<state>
L2_CURRENT_STATE=<state>
L2_INTERFACE=<logical interface>
L2_ATTACHMENT_INTERFACE=<actual interface>
L2_IFINDEX=<ifindex>
L2_INTERFACE_GENERATION=<generation>
L2_EVIDENCE_ID=<event-id>
L2_EVIDENCE_STATUS=<stored|partial|unavailable>
MESSAGE=<short human-readable summary>
```

MAC addresses, IP addresses, packet bytes, fingerprints, raw topology, PCAP paths, and adapter error chains are prohibited from alert fields and `MESSAGE`.

The daemon emits alerts only when an event opens, changes state, closes, or output health changes. It does not emit periodic reminder alerts in the first release. Internal repeated observations update bounded in-memory counters and the next material evidence snapshot.

If the journald socket is unavailable at startup or becomes unavailable, the daemon writes the same sanitized event as one newline-delimited JSON object to stderr. Logging failure never stops detection or evidence persistence. Journald delivery remains best effort; the evidence store remains authoritative.

## 10. Control and CLI Contract

The evidence shapes in the foundation are placeholders and have not been distributed. This design replaces those shapes before the first release while keeping `protocol_version: 1`. Contract tests change atomically with implementation; after the first release, incompatible evidence changes require a new protocol version.

### 10.1 Status

`l2-loopctl status [--interface <IFACE>] [--json]` returns, per interface:

- observation and loop state;
- captured-at and last-transition timestamps;
- data-freshness state;
- active event and evidence IDs;
- evidence store health;
- last sanitized persistence error code;
- journald connection or fallback state;
- the count of alerts intentionally suppressed by state deduplication.

The daemon cannot know whether journald later rate-limited a successfully submitted message, so status must not claim end-to-end journal delivery.

### 10.2 Evidence list

```text
l2-loopctl evidence list \
  [--interface <IFACE>] \
  [--limit <1-200>] \
  [--cursor <OPAQUE>] \
  [--json]
```

The default limit is 50. Results are ordered by last-transition time descending and event ID descending. The response contains sanitized `EvidenceSummaryV1` values and an optional opaque `next_cursor`. A cursor is bound to the filters used to create it; malformed or mismatched cursors are rejected.

### 10.3 Evidence show

```text
l2-loopctl evidence show --id <EVENT_ID> [--json]
```

This returns a sanitized detail view and attachment metadata, never raw PCAP bytes. Full root-only evidence remains available on the local filesystem for authorized incident handling. Stable errors distinguish `not_found`, `corrupt`, `permission_denied`, and `store_unavailable`.

Every encoded response must remain below the one-megabyte frame cap. Listing is bounded before serialization; the daemon does not build an unbounded vector and then discover that the response is too large.

## 11. Component Boundaries

`l2-loop-core` owns:

- `EventId` and its strict parser;
- `AlertEventV1`, `EvidenceSummaryV1`, and sanitized detail models;
- severity, evidence status, store health, and stable error enums;
- paginated protocol-neutral command and result types.

`l2-loop-agent` owns:

- `EventRecorder<S, L>` orchestration across an evidence store and alert sink;
- `EvidenceStore::put`, `get`, `list`, and `health` ports;
- a Linux filesystem evidence adapter;
- a journald alert sink with JSON-stderr fallback;
- authorization from Unix peer credentials;
- retention, recovery, and the in-memory evidence index.

`l2-loop-cli` owns:

- pagination arguments and cursor forwarding;
- human and stable JSON rendering;
- clear output-health and evidence-integrity messages.

The state machine produces typed transitions but does not write files or call journald directly. The filesystem adapter does not decide severity. The CLI does not read `/var/lib/l2-loop/evidence/` directly.

## 12. Failure Semantics

| Failure | Required behavior |
|---|---|
| Evidence root missing or unsafe | Do not repair ownership implicitly; report store unavailable |
| Disk full or quota exhausted | Drop optional PCAP first, evict eligible closed events, then degrade without blocking detection |
| Partial write or crash | Current view is either the previous valid revision or the new valid revision; never a mixed view |
| Corrupt committed revision | Exclude it from normal queries, use the highest earlier valid revision, report corrupt count, and preserve it for root review |
| Event ID collision | Do not overwrite; generate a new ID and record an internal sanitized warning |
| Journald unavailable | Emit newline-delimited sanitized JSON to stderr |
| Journald rate limiting after submit | Not detectable by the daemon; durable evidence and CLI remain available |
| CLI requests a malformed ID | Reject before filesystem access |
| CLI response would exceed one MiB | Bound list/detail before serialization and return a stable size error if still impossible |
| Daemon restarts | Rebuild the bounded index from validated manifests and preserve event history |

An alert publishing failure never changes an XDP or TC verdict. Observation remains fail-open.

## 13. Test Contract

Pure domain tests cover:

- canonical `EventId` parsing and path-like input rejection;
- schema-version and enum serialization;
- severity mapping and evidence-status rules;
- stable ordering and cursor/filter binding;
- sanitization of summaries and journal fields.

Filesystem adapter tests use a temporary directory and injected failure points to cover:

- failure after every write, `fsync`, and rename step for both the first event and later revisions;
- no-replace collision behavior;
- restart with a valid bundle, temporary bundle, corrupt manifest, wrong length, and wrong SHA-256;
- root and file modes;
- symlinks, non-canonical names, and path traversal attempts;
- disk-full and every quota boundary;
- PCAP omission before structured-evidence loss;
- retention order and active-event protection;
- concurrent `put`, `list`, and `get` calls.

Alert-sink tests cover:

- exact native journald field mapping;
- prohibited-field scans;
- one event per material transition;
- stderr JSON fallback;
- evidence stored, partial, and unavailable states;
- output-health transitions without recursive alert storms.

Protocol and CLI tests cover:

- default and maximum limits;
- stable pagination under equal timestamps;
- malformed, expired, and filter-mismatched cursors;
- sanitized list and detail output;
- `not_found`, `corrupt`, `permission_denied`, and `store_unavailable` errors;
- responses at and above the frame-size boundary.

One end-to-end test drives:

```text
fake loop-state transition
  -> real EventRecorder
  -> temporary filesystem store
  -> fake alert sink
  -> real Unix control socket
  -> real CLI client and renderer
```

The same test is repeated with injected evidence persistence failure and proves that the alert reports `evidence_status=unavailable` and `status` reports degraded output health.

GitHub-hosted tests require no root, live network interface, systemd daemon, or `/var/lib` access. Authorized Linux acceptance later verifies actual journald fields, filesystem modes, restart recovery, and group/root access separation.

## 14. Performance Rules

- No evidence I/O runs in the packet path.
- A state transition copies only bounded snapshots from the analysis layer.
- Blocking file operations run outside Tokio async workers.
- Filesystem writes are serialized per event; different events may proceed independently within a small fixed concurrency limit.
- The in-memory index stores summaries, never PCAP or full evidence payloads.
- List queries use the index and pagination; they do not deserialize every bundle.
- No unbounded channel, vector, label set, or retry queue is permitted.

The first implementation does not add a background database writer. State transitions are rare relative to packet samples, so a bounded filesystem task is the simpler and safer design.

## 15. Security and Privacy

- The daemon remains the only normal reader and writer of the evidence store.
- Unix peer credentials distinguish root from the read-only `l2-loop` group.
- Read-only group responses are sanitized, including JSON mode.
- Raw evidence and PCAP are root-only and never logged.
- User input never becomes a path component without `EventId` parsing.
- Unknown filesystem objects are preserved and reported, never cleaned broadly.
- Error responses expose stable codes and concise messages, not raw paths or error chains.
- Evidence integrity hashes detect corruption; they are not authentication signatures.

## 16. Delivery Boundary

This design is ready for a dedicated implementation plan. That plan must preserve test-first GitHub-only compilation and split delivery into domain contracts, atomic store, event recording and journald, paginated CLI, and authorized Linux acceptance.

Explicitly deferred:

- Prometheus and monitoring-platform metrics;
- Alertmanager and remote notification adapters;
- raw PCAP export commands;
- configurable periodic reminder alerts;
- database-backed indexing;
- cross-node event correlation.
